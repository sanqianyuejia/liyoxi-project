### 2.3 处置说明的写法

每条规则在本节下加一小节，按下面的栏写。默认：小节标题用“规则 N <名称>”（W0-04 定）。

| 栏 | 写什么 |
| --- | --- |
| 现象 | 告警长什么样；常见的伴随告警 |
| 先看 | 哪张表、哪个页面、哪条日志（按 `reqId` 查） |
| 判断 | 几种常见原因各自的特征 |
| 处置 | 每种原因的步骤；用到的 CLI |
| 不要做 | 会把事情弄糟的动作 |
| 升级 | 多久没恢复找谁 |
| 事后 | 要不要补不变量校验、补对账、记一条演练或事故记录 |

### 2.5 备份、证书与P95操作

W2-27经授权把备份只读连接、公钥收件人文件、桶/前缀和明确域名挂给worker；stg/prod只认敏感URL_FILE。先以既有库权限核对确认登录角色是lyx_readonly成员、没有写权限，公钥文件不含私钥。没有任何一项时本包失败/未配并留事实，不临时借asset桶或应用写账号。私钥仍在两位E14保管人手中，worker不读取。

03:10 backup.pgdump使用现server镜像PostgreSQL17客户端和age；原job租约续租/三次重试。观察timer.result的key/bytes/seconds/pgDumpVersion/etag/monthlyKey，与HEAD大小和上一成功摘要比较。失败先查客户端版本、只读权限、公钥/桶配置与StorageProvider错误类别；不要把上传完成当解密恢复已经做过。月首保留monthly副本。

09:00 ops.cert_check只检查CERT_DOMAINS指定DNS的443证书；无域名=unconfigured，连接不可达/不可信也不是到期健康。凭部署摘要找到受影响域名，续签/重载必须按授权操作，随后观察真实检查与恢复轮次。注入TLS假响应仅证明代码分支。

P95本机/CI入口是 `APP_ENV=test node infra/ci/p95.mjs --concurrency 20 --scale 10 --seed 42`，前置仅公开本机PG/Redis测试连接。既有owned守卫新建本轮隔离库/Redis前缀，真实订单/账本原型加历史配套、UUID精确映射短TX图复制，当前全部可运行full检查91项/17模块（同步后的approval.I3/I5均保留）；flow.STUCK_TICKET仅上报端口。原型出站事件经既有真实中继/消费路径排空；无匹配的已实现订阅者时消费0如实记录，不能称云通知已发。约5000店/2万订单/98万流水，精确表/type数写报告。付款创建现只新开通，额外100个有完整资格历史的新购门店单列，HTTP采样前再次全91校验覆盖全部新增输入，不伪造active套餐续费；演示银行占位经过真实双人审批，不涉及外部支付。真实TCP HTTP/鉴权/限流/幂等保留，100样本/接口，500ms或错误非0，未来工作台四路逐项excluded→G7-B/M7未拆编号读侧包。小烟测不可替代默认规模验收。

nightly独立p95 job冻结安装、生成客户端、准备本作业PG/Redis、正反例、默认测量、always上传报告；失败产生GitHub作业红与错误报告，保留Node26原检查/required名单。失败先看报告前置/不变量/错误率/逐接口P95与机器load，再定点查索引和聚合；不能调高500ms、缩规模或择优重测。预发2核/1.87GB与实际云通道验收仍留D7-16/V17，不能拿本机数字关闭。

### 5.3.1 逻辑备份恢复方法（尚未真实演练）

1. 经授权选择明确成功timer摘要与对象key，下载加密对象，核对摘要大小/etag、月首副本和来源版本；不操作正在使用的库。
2. 两位E14保管人取离线私钥到隔离临时环境，用 `age --decrypt --identity <离线身份文件> --output <本轮临时dump> <已核对的加密对象>`；私钥不上传服务器。解密失败立即停止，不能换未验证文件。
3. 经授权建独立空实例/库，使用同主版本PostgreSQL17 `pg_restore --no-owner --dbname <本轮空库连接> <临时dump>`；目标连接由受控文件/环境提供，不记录凭据。约束/恢复报错非成功。
4. 以对应迁移工具核 `prisma migrate status`、结构/权限/分区；在恢复库跑实际full不变量，比较源备份摘要、单号序列、账本余额/持有/分配/付款引用。任何不一致停止切换。
5. 完成授权切换与业务核对后，把私钥归还离线保管、清理明确本轮临时明文dump和临时环境；记录第6.1节真实耗时/结果。当前代码测试只证明加密上传及本地流程分支，未执行真实离线解密/生产恢复。

本包 b1 的本机方法为 pnpm stg:rehearse -- --release：另造两个真实构建号的 server/gateway，在随机project/网段/回环端口与假密钥目录内，初始版幂等发布登记、发布新版、缺省回滚，检查 /health 新→旧以及新旧全部资源。每次编排给 --probe-config <目标JSON> / --probe-summary <报告JSON>，每秒探测 API 两条真健康、匿名商城配置和两个前端入口；编排传真实启动者 PID，使 READY 前失父也退出并保存最终 JSON。全资源按实际镜像清单逐个比sha256。库核对复用原 grants、constraints、partitions；缺一个部分索引必须变红，恢复后再次通过。迁移前持久化 db-release.env 的目标，回滚不改该记录；核库工具与快照使用该迁移版本，应用版本仍是回滚目标，CI 的 dbVerification 分别列出。prune 保留三版运行镜像之外，也保护这份数据库 server 工具镜像。证据保存在单独自有临时目录，清场只删本次project/卷/容器/镜像标签。b2a 已从 W2-25b 实际主干交付私有固定上传器消费者。b2b 独立 gate-change 已接 .github/workflows/deploy-stg.yml：它只取同仓 main 成功 images push run 的同 source，编排完成（含 verify-db）后才串行调用 weapp-upload。CI 的 STG_WEAPP_UPLOAD_ENABLED 与节点 LYX_WEAPP_UPLOAD_ENABLED 均默认关闭；未配桶时跳过并保留摘要。节点只接受完整 source 与 images.json 的 SHA256，私有 COS reader 验同源摘要及归档，上传器再核当前成功部署、公开构建配置与真实镜像摘要；机器人固定 1，不打标签。手动 .github/workflows/rollback-stg.yml 同样只在 main 且显式开关/execute 确认时执行，与部署共用 deploy-stg 串行锁，STG_FREEZE 和原安全拒绝仍生效。探测目标由 STG_PROBE_CONFIG 提供已登记的 JSON，持续探测与发布/回滚摘要均保存。固定工具、公开配置与凭据文件的未来配置见 infra/bootstrap/cos-adapter/README.md；本机桩 SDK/HTTP 结果不填成预发实跑记录。预发执行仍须按任务书第 8 节由业主执行或在场逐步授权；本地目标测试不等于预发实跑。
